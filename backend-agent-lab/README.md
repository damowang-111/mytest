# Python 后端与 Agent 场景题单（实习面试）

这是一套可动手实现的题目，**不含答案**。业务数据是为练习构造的模拟数据，不代表任何真实公司的内部指标。你可以用 FastAPI、Django 或其他 Python 框架；数据库驱动、ORM、Agent 框架由你选择。允许用固定响应的假模型替代付费 LLM，但需要保留真实的调用边界、延迟和失败行为。

## 使用方式

1. 安装 Docker Desktop，进入本目录执行 `docker compose up -d`，启动 MySQL、Redis 和 RabbitMQ。
2. 按题目需要启动额外服务：
   - 对象存储：`docker compose --profile storage up -d`
   - 向量检索：`docker compose --profile agent up -d`
   - Kafka：`docker compose --profile stream up -d`
3. 用 `docker compose ps` 查看状态。RabbitMQ 控制台：<http://localhost:15672>；MinIO 控制台：<http://localhost:9001>；Qdrant：<http://localhost:6333/dashboard>。
4. 每题单独建目录，至少保存 `README.md`、建表/造数脚本、启动命令、压测或故障注入脚本，以及一份运行结果。下一题可复用前面的表和代码。
5. 用 `docker compose down` 停止；`docker compose down -v` 会清除这套练习的持久化数据。

| 服务 | 本机地址 | 练习账号 |
|---|---|---|
| MySQL | `localhost:3306/service_lab` | `lab / lab_dev_123` |
| Redis | `localhost:6379` | 无密码，仅绑定本机 |
| RabbitMQ | `localhost:5672`，管理页 `:15672` | `lab / lab_dev_123` |
| MinIO（可选） | API `localhost:9000`，控制台 `:9001` | `labadmin / lab_dev_123456` |

这些账号只用于本机练习。Compose 没有打包 Python 应用或付费模型。端口被占用时，修改 `compose.yaml` 中冒号左侧的宿主机端口，应用连接地址也要同步修改。

## 统一业务背景与数据口径

你在做一家电商的售后平台。用户下单后可发起退款、物流查询、商品咨询；客服工作台和 AI 客服共同处理工单。高峰发生在每天 20:00–22:00。下面的“业务规模”是题目背景；“本地数据”是推荐造数规模，可在普通开发机逐题运行。

| 对象 | 业务规模 | 本地数据与分布 |
|---|---:|---|
| 用户 | 12 万 | 1 万；其中 20% 的用户产生 65% 的请求 |
| 商品 SKU | 8,000 | 800；其中 20 个热门 SKU 占 35% 的浏览 |
| 订单 | 120 万，日新增约 4 万 | 10 万；近 7 天占 30%，`PAID` 55%、`SHIPPED` 30%、其他 15% |
| 订单明细 | 约 350 万 | 30 万；每单 1–5 条，随机但可复现 |
| 工单 | 30 万，日新增约 6,000 | 3 万；退款 40%、物流 35%、其他 25% |
| 工单消息 | 约 240 万 | 24 万；每单 1–15 条，少数长会话超过 100 条 |
| 知识文档 | 5 万篇 | 5,000 篇；物流、退款、发票、活动规则四类 |

建议统一使用 `user_id`、`order_id`、`sku_id`、`ticket_id`、`tenant_id`、`created_at` 等字段，并固定随机种子以便复现。时间戳使用 UTC 存储；展示时转换时区。金额用整数分或精确十进制类型。各题如果给出额外数据分布，以该题为准。**造数脚本、故障注入和测量方法也是练习的一部分**；不要只写接口的正常路径。

每题请记录：初始假设、最小可运行 Demo、输入数据、触发步骤、观察到的日志/指标、改动前后结果，以及仍未解决的问题。性能题至少重复测量并记录环境与并发数，不要求得到某个固定毫秒数。

## A. MySQL 与数据正确性

### 01｜售后工单列表突然变慢

**场景数据：** 客服按 `tenant_id=7`、状态 `OPEN`、最近 30 天筛选工单，按创建时间倒序取前 20 条。业务库 30 万工单，本地先造 3 万，再放大到 30 万；租户 7 占 45%，`OPEN` 占 20%。高峰 80 次查询/秒。产品反馈列表从 100 ms 左右变为 2 s 以上。

**任务：** 建表、造数并实现 `GET /tickets`。先复现一个明显偏慢的查询，再分析并调整查询或存储设计。筛选结果和排序必须正确。

**交回证据：** 建表 SQL、查询 SQL、执行计划、不同数据量下的耗时分布、调整前后结果一致性的验证。

### 02｜翻到第 3000 页时接口超时

**场景数据：** 客服要导出一个租户近 90 天的 20 万条订单；每页 50 条。订单在翻页期间仍持续写入，每分钟新增约 30 条。页面可以跳页，导出要求不重不漏。

**任务：** 分别实现管理页面浏览和完整导出；复现深页变慢及并发写入下的数据边界问题，明确两个功能各自的正确性要求。

**交回证据：** 首页、深页耗时；导出总数、唯一 ID 数、重复/遗漏检查；并发插入期间的复现实验。

### 03｜订单列表上线后数据库连接数飙升

**场景数据：** 列表一次返回 50 个订单，每个订单平均 3 个明细、1 条物流摘要。高峰 100 次请求/秒，数据库连接池上限 30；接口 p95 从 180 ms 升至 1.5 s。

**任务：** 实现一个会触发该现象的订单详情组装接口，定位请求内查询次数和连接占用，再修正。响应字段保持不变。

**交回证据：** 单请求 SQL 次数、并发下连接池指标、改动前后接口响应样例和耗时。

### 04｜最后一件库存被卖出两次

**场景数据：** 某 SKU 库存仅剩 1 件，100 个用户在 200 ms 内同时提交订单。支付服务用可控假实现：10% 超时、5% 明确失败，其余成功。业务要求可售库存不为负，成功订单与扣减结果一致。

**任务：** 实现 `POST /orders` 与支付结果处理，构造并发竞争及失败路径。你需要决定订单创建、扣库存、支付确认分别发生在什么时点。

**交回证据：** 100 次并发请求的结果统计、最终库存、订单状态分布、失败和超时后的核对记录。

### 05｜用户连点“申请退款”

**场景数据：** 用户 2 秒内发出 5 次相同退款请求；网关还会在 3 秒超时后自动重试 2 次。退款平台接口可能“处理成功但响应丢失”。同一订单最多只能产生一笔有效退款。

**任务：** 实现退款申请和状态查询；模拟重复请求、重试、响应丢失和服务重启。定义客户端如何表达“同一次业务操作”。

**交回证据：** 每次请求的响应、数据库退款记录数、模拟平台调用次数、重启前后的行为。

### 06｜事务提交后通知没有发出去

**场景数据：** 工单状态变为 `CLOSED` 后要给用户发送通知。每天 6,000 次变更；通知允许延迟 1 分钟，不能永久漏发。进程可能在“数据库提交完成”与“通知送出”之间随时退出。

**任务：** 做出最小可运行流程，注入该时间窗口内的崩溃，并设计可恢复的处理链路。通知消费者也可能收到重复事件。

**交回证据：** 故障注入点、重启后的工单与通知记录、重复投递时的最终结果。

## B. Redis 与高并发接口

### 07｜热门商品详情把 MySQL 打满

**场景数据：** 20 个热门 SKU 承担 35% 的浏览；单个热门 SKU 峰值 500 次/秒。商品价格每天改 2 次，库存随订单变化。商品详情允许价格最多旧 30 秒，库存展示最多旧 3 秒。

**任务：** 实现商品详情接口和两类字段的更新路径；造出热点流量，验证读吞吐、数据库压力和数据新鲜度。

**交回证据：** 缓存命中率、数据库查询数、商品更新后的可见延迟，以及故意制造更新失败后的表现。

### 08｜缓存同时过期造成突发流量

**场景数据：** 1 万个商品缓存由批任务在 20:00 写入，过期时间都是 30 分钟。20:30 的 10 秒内有 2 万个请求，MySQL 可稳定处理 300 次查询/秒。

**任务：** 复现过期时间集中带来的峰值，并使系统在相同请求模式下保持可用。要同时覆盖一个特别热门的 key 和大量普通 key。

**交回证据：** 每秒缓存命中/未命中、MySQL 查询量、接口错误率、负载曲线。

### 09｜不存在的订单号被大量查询

**场景数据：** 正常订单查询 200 次/秒；攻击流量另有 1,000 次/秒，90% 是随机且不存在的订单号。合法的新订单每秒仍在生成。

**任务：** 实现查询接口，阻止无效请求穿透到数据库，同时保证刚创建的合法订单可以尽快查到。加入用户只能查看自己订单的检查。

**交回证据：** 正常与异常流量下的数据库 QPS、合法订单创建后可见时间、越权请求结果。

### 10｜定时任务在两台实例上重复执行

**场景数据：** 每分钟扫描并关闭超过 7 天未回复的工单，单次扫描通常需 20 秒，偶尔持续 80 秒。服务有 2 个实例，某实例可能在处理第 40 条时崩溃。

**任务：** 用两进程模拟定时任务竞争、超时和崩溃；确保最终每个应关闭的工单状态正确，且可继续处理未完成的部分。

**交回证据：** 两进程日志、崩溃前后已处理/未处理数量、重复执行统计、最终数据库核对。

## C. 消息队列与后台任务

### 11｜消费者处理一半就崩溃

**场景数据：** 订单支付后发布 1,000 条“发优惠券”事件。消费者每条处理耗时 50–300 ms；其中 2% 因上游错误失败，0.2% 为永远无法解析的数据。消费进程会被手动中断两次。

**任务：** 用 RabbitMQ 实现生产与消费，定义成功、可重试失败、不可处理消息的去向，并保证最终发券记录可核对。

**交回证据：** 发布数、确认数、重试数、异常消息数、最终发券唯一记录数及中断恢复日志。

### 12｜支付事件乱序到达

**场景数据：** 同一订单的 `CREATED`、`PAID`、`REFUNDED` 事件可能按 `PAID → CREATED → REFUNDED` 顺序抵达；部分消息重复。不同订单可以并行处理。

**任务：** 实现订单状态投影消费者。输入 100 个订单，每单 3–5 个状态事件，随机打乱、重复后投递。

**交回证据：** 输入事件文件、最终状态核对表、乱序与重复事件的处理日志。

### 13｜邮件任务积压到第二天

**场景数据：** 活动期间每分钟新增 3,000 个通知任务；当前 worker 每分钟处理 1,000 个。普通营销邮件可延迟 1 小时，退款成功通知须在 2 分钟内送达。邮件服务每 100 次调用有 3 次超时。

**任务：** 做出任务生产、消费与优先级/隔离策略；模拟 15 分钟流量并观察积压与恢复。定义超过时效的任务怎么处理。

**交回证据：** 两类任务的等待时间分布、队列深度时间线、超时与恢复记录。

### 14｜Kafka 消费者下线后追不上流量

**场景数据：** 订单行为流每秒 500 条，消息体约 1 KB。统计服务下线 20 分钟，恢复时仍有实时流量；业务要求 30 分钟内赶上，并保证每日成交额统计可核对。

**任务：** 用 Kafka（`stream` profile）做生产、消费和按天统计。模拟消费者停机、恢复、重复读取及代码重启。

**交回证据：** offset/lag 变化、赶上所需时间、每日日汇总与 MySQL 原始订单的对账结果。

## D. API、文件与可观测性

### 15｜活动接口被脚本刷爆

**场景数据：** 正常用户每分钟查询 5–20 次；一个脚本从同一 IP 使用 500 个账号，每秒发 300 次请求。API 的正常容量约 150 次/秒，客服内部账号需要更高额度。

**任务：** 实现一个对外 API，设计并验证限流规则和返回语义。演示单实例与两实例运行时的结果。

**交回证据：** 各类身份的通过/拒绝数、两实例下的总通过量、正常用户误伤情况。

### 16｜物流服务偶发慢响应拖垮接口

**场景数据：** 物流服务平时 80 ms 返回；10% 的请求耗时 5 s，另有 2% 返回 500。你的订单详情接口要求 p95 小于 800 ms，最多同时处理 100 个请求。

**任务：** 写可配置延迟和错误率的假物流服务，再实现调用方。连续压测 5 分钟，观察依赖异常前后接口与资源占用。

**交回证据：** p50/p95、成功率、同时在途请求数、连接占用、异常恢复时间。

### 17｜用户上传 200 MB 证据视频

**场景数据：** 售后证据包含图片和视频；单文件上限 200 MB，日上传约 5,000 个，总量约 80 GB。上传中断率 8%；用户可能上传同名文件，且只能读取自己的证据。

**任务：** 使用 MinIO（`storage` profile）实现上传、元数据保存、下载鉴权和中断后的处理。测试超限、同名、重复提交、删除及越权访问。

**交回证据：** 对象存储中的文件清单、数据库元数据、失败后残留对象、鉴权测试结果。

### 18｜线上偶发 502，日志却查不出原因

**场景数据：** 一个请求依次经过 API、MySQL、Redis、RabbitMQ；每分钟 1 万请求，错误率约 0.5%。其中部分错误是超时，部分是数据库连接耗尽。

**任务：** 给你已做的任一接口加入可关联的请求日志与基础指标，注入两类故障，并写一个“从报警到定位”的排查记录。

**交回证据：** 一条完整请求的关联日志、错误率和延迟曲线、两类故障的定位时间及依据。

### 19｜多租户数据串到了别家店铺

**场景数据：** 平台有 100 个商家；`order_id` 在全平台唯一，但商品编码只在商家内唯一。某接口按商品编码查订单，商家 A 看到了商家 B 的订单汇总。

**任务：** 实现有意包含该缺陷的查询，再加上服务端租户隔离。覆盖列表、详情、导出、缓存 key 四条路径。

**交回证据：** 两个商家的样例数据、修复前后越权请求响应、自动化隔离检查。

## E. Agent、RAG 与工具调用

### 20｜AI 客服检索到了过期退款政策

**场景数据：** 知识库 5,000 篇文档，每篇切分成 3–10 段；其中 15% 有新版，旧版必须在新规则生效后退出检索。测试集 100 条问句，含 20 条需要准确引用生效日期。

**任务：** 使用 Qdrant（`agent` profile）构建入库、更新、检索、回答 Demo。可以用确定性假模型生成回答，但检索和引用必须真实运行。

**交回证据：** 文档版本样例、检索结果、100 条问句的命中/引用统计、更新前后对比。

### 21｜相似问题能检索到，但答非所问

**场景数据：** 用户问“签收后 8 天还能退吗？”；知识库同时存在“7 天无理由”“质量问题 15 天”“生鲜不支持无理由”三类规则。测试集 60 条，其中 15 条信息不足，必须追问而不能直接下结论。

**任务：** 构建一个可重复的离线评测集，比较至少两种检索/回答配置；记录错误类型，给出你选择配置的依据。

**交回证据：** 评测数据格式、每条问句的命中文档与回答、准确/误答/应追问统计。

### 22｜Agent 调用退款工具时参数错了

**场景数据：** 用户同时有 3 个订单，其中 2 个金额相同。用户说“退掉昨天买的那个”，Agent 只能读取当前登录用户的订单；退款工具一旦执行就会生成真实业务记录。测试输入中混入 10 条诱导其操作其他用户订单的提示。

**任务：** 实现查订单与申请退款两个工具，建立参数校验、权限边界和执行前确认流程。用假模型也可，但需要真实工具调用和真实数据库状态变化。

**交回证据：** 工具调用轨迹、歧义订单时的交互记录、越权输入测试、数据库退款记录。

### 23｜Agent 对话流中途断开

**场景数据：** 一次对话会先检索知识库，再调用物流工具，最后流式返回回答。工具调用偶尔耗时 8 s；10% 客户端在 2 s 内断开，5% 在工具执行后断开。后台同时有 50 个会话。

**任务：** 实现流式接口和取消/重连场景。明确断开后后台工作与外部工具操作如何处理，避免同一操作被重复执行。

**交回证据：** 50 并发下连接数、断开与重连日志、工具执行次数、客户端最终可见内容。

### 24｜模型变慢且成本突然翻倍

**场景数据：** 每天 6,000 次 AI 客服会话；原平均 3 次模型调用、总计 6,000 tokens/会话。新版本平均 5 次调用、11,000 tokens/会话；回答正确率可能提升，也可能下降。假模型可按字符或预设 token 数计费。

**任务：** 建立调用级日志和离线评测，比较两个版本的质量、延迟与估算费用。设计一个可复现的回归门槛，并用故意退化的版本测试门槛是否生效。

**交回证据：** 逐会话调用记录、质量/延迟/费用汇总、回归判定结果与失败样例。
